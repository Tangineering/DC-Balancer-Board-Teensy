## 2. Answers to the operator's questions

**Is the Ag105 powered by default on the current firmware?** No. The board gives the charger
input power through only two switches: `FC_CHARGE_ENABLE` (bus -> charger, through D-BC-FC) or
`REGEN_ENABLE` (motor node V-MOT -> charger, through D-BC-RG). The firmware's own test is
`chargerHasPower() = FC_CHARGE || (REGEN && MOT_PWR)` (:14670). On v35/v36:

- `FC_CHARGE` never opens in Run (`FC_CHARGE_ALLOWED 0`, :2492); it opens only for the 10 ms
  State-99 cap drain and the State-98 `'5'` key.
- `REGEN` opens only while the commanded motor current is below -0.1 A (:13747).

So in Init, Idle and almost all of Run the Ag105 has **no input power**, cannot answer I2C, and
telemetry reports `charger_status` 0 and `I_charge` 0. It is powered only for the brief REGEN
flickers (20-200 ms in the bags). The firmware waits 500 ms of continuous power
(`AG105_SETTLE_MS`, :2360) before it trusts or configures the charger, and every power loss
resets that, so on this board the charger has never been configured from firmware in any
recorded run. Its EPROM may still hold the factory default (4.2 V / 1 A), which would not charge
a 2S pack at all. That is why the B1 bench test (section 3.1) comes first.

**What "the bus feeding the charger" means (R3).** The motor node V-MOT is connected to the
16 V bus through the `MOT_PWR` ideal-diode switch, which is kept closed through Idle and Run
(the Death-5 pre-charge rule). So whenever the firmware closes `REGEN`, the charger's input sees
the bus voltage (~15.8 V), regen or not. The bags show exactly this: during every REGEN tick
V_chg read V_bus - 0.09 V while the regen node was flat. If the charger were configured and
enabled at that moment, it would draw its charge power (up to ~24 W, ~1.5 A of bus current at
2.5 A charge) **from the bus, i.e. from the fuel cell and battery boosts**, not from braking:

- the battery share is a loop (battery -> BT boost -> bus -> charger -> battery) that only loses
  energy (two conversions at ~88 % each);
- the fuel-cell share is FC -> pack charging, which `FC_CHARGE_ALLOWED 0` was meant to forbid;
- it is a large new bus load that the UV backoff does not currently cover (regen outranks it,
  :13784 before :13806).

The ruling R3 asks: is any of that ever wanted (for example as a deliberate way to test the
charger), or must the firmware guarantee the charger only takes energy when V-MOT is ABOVE the
bus (genuine regen)? The threshold method in section 3.2 gives that guarantee in the charger
itself, provided the threshold sits above the bus; a held REGEN arm without it does not.

## 3. Regen: findings, measurements, and the fw v37 design

### 3.1 Bench gate B1 (zero code, State 98) - run before any regen firmware change

`G` (bus and motor node up) -> `4` (REGEN HIGH: the charger now has ~15.8 V from the bus) ->
wait >= 5 s -> `I` (does 0x30 ACK?) -> `S` (status byte, CHARGER_STAT, `ag105Configured`,
I_charge) -> `N` (reg 0x02 threshold, input voltage) -> `M` (release MPPT) -> `S` -> `4` off.
Clamp-meter the charger's VBAT+ lead; watch I_batt and V_bus. Also: DMM on VCHG with BT_SEQ
high and the charger unpowered (D-BT-SQ orientation: ~0 V = schematic, ~pack voltage =
reversed); DMM on V-MOT vs the pin-39 reading (the V_rgn 0.85 scale).

| B1 outcome | Meaning |
|---|---|
| No ACK at 0x30 | charger power or I2C problem; firmware cannot help |
| ACK, status 0x00, STAT 1 pulse, no current | consistent with the VBat- wiring defect (R2) |
| ACK, charges from the bus | the charger works; the remaining blockers are firmware timing and test design |

### 3.2 The operator's concern: is the Ag105 fast enough for a regen burst?

What the bags show about the burst (RegenTest_v2, six decels from 2 m/s, fw <= v35,
`docs/reviews/fw36_regen_2026-11-04/figs/regentest_decels.png`): V-MOT rises 0.08-0.12 s after
the setpoint falls, peaks at the chopper clamp (~21.4 V true) 0.10-0.20 s in, and is back at bus
level by 0.3-0.6 s. Braking work above friction is ~0.8-1.0 J per decel, ~0.7 J electrical:
roughly 0.2 A into the pack for 0.4 s, if captured.

What the datasheet says (AG105_Silvertel.pdf, MPPT section): the threshold (11-33 V, reg 0x02 or
MPPTS) "must be present across the input ... before charging will commence"; MPPT "can be enabled
or disabled without restarting the module or terminating charge". **It gives no response time,
no start-up time and no Bring-Up duration.** So the concern is real and unanswerable from the
documents: `TODO(verify: Silvertel)` and measure.

The threshold method removes the firmware's 500 ms settle and the module's boot time (the charger
stays powered and configured), but not the module's own reaction time to its input crossing the
threshold, nor any Bring-Up phase it runs at the start of each charge.

**Measurement M1 (decides R1):** after B1 passes, in State 98 with REGEN held and the charger
configured: set reg 0x02 just above V_bus (`N`), release MPPT, then step the threshold below
V_bus and back above (two `N` writes). Scope the charger input current (or VBAT+ current) and
time onset and release. Then repeat on a real RegenTest decel with a 1 kHz `'K'` BLG running.

| M1 result | Consequence |
|---|---|
| Onset << 100 ms | threshold method is viable as designed |
| Onset ~ 100-300 ms | captures only the tail of each burst; consider lengthening the burst: a lower VESC "Battery Current Regen Max" (longer, gentler braking), or more V-MOT capacitance (hardware) |
| Onset > ~0.5 s or a Bring-Up per event | the Ag105 cannot harvest these bursts on this board; regen harvest needs a hardware path or a different charger; keep the firmware diagnostics only |

### 3.3 fw v37 regen design (R3 = no bus-fed charging; R1 pending M1)

**The Ag105 has no charge enable.** Table 7 lists no enable/disable register (0x00 current,
0x01 voltage, 0x02 MPPT threshold, 0x03 timeout, 0x04 recovery, 0x05-0x07 measurements, 0x0A
JEITA, 0xE5/0xE6/0xFD/0xFE housekeeping), and the module's only control pins are MPPTD and LD
(load output disable). So "the charger decides not to charge" can only mean its input threshold
(reg 0x02, EPROM, written over I2C), and that threshold may not even apply while MPPTD is LOW,
which is exactly how v35/v36 hold it during regen. A threshold is a setting, not an interlock:
it was never acceptable as the only thing standing between the bus and the charger.

**Why the hazard exists at all.** V-MOT is both the motor's supply and the regen node. With
`MOT_PWR` closed (kept closed through Idle and Run since Death 5), closing `REGEN` connects the bus
to the charger input. Scale of the loop: bounded by the charger's own current limit (2.5 A charge,
~24 W input, ~1.5 A of bus current), so it is not a runaway, but it wastes ~25 % of what it
circulates, draws FC power into the pack (what `FC_CHARGE_ALLOWED 0` forbids), loads the FC toward
its 1.4 A OC trip, and sits outside the UV backoff today.

**Design rule for fw v37 (R3):** the regen switch may be closed only while the bus CANNOT supply
the charger, i.e. while braking holds V-MOT above the bus. The RT1987s have back-to-back MOSFETs
(RT1987 DS, "true reverse current blocking"), so a switch held off blocks both directions and a
firmware interlock on `REGEN_ENABLE` is a real physical break.

- **Layer 1 (primary, firmware interlock at 1 kHz):** close `REGEN` only when calibrated
  V_rgn > V_bus + margin (MOT_PWR's ideal diode is then reverse-biased, so no bus current can flow
  to V-MOT), and open it as soon as V_rgn falls back toward V_bus. Requires the V_rgn calibration
  (the 0.85 scale) first, and the decision must run in the 1 kHz loop, not the 50 Hz
  `chargingControl()`. Cost: the charger is unpowered until the burst starts, so its boot time
  eats into a 0.3-0.6 s burst (M1 measures how much).
- **Layer 2 (independent, in the charger):** reg 0x02 set above the bus (e.g. 17.86 V) with MPPT
  RELEASED while REGEN is closed, so a layer-1 failure still finds the charger refusing a ~16 V
  input. Never hold MPPTD LOW with REGEN closed until the datasheet question "does MPPTD-low bypass
  the threshold?" is answered. Note the factory default (0xFF with MPPTS open = 18 V) is also above
  the bus; a v24-era EPROM write could have left 12.3-13.4 V, so read reg 0x02 back before relying
  on it.
- **Layer 3 (backstop detector):** while REGEN is closed, if V_rgn is within the margin of V_bus,
  or the bus sources deliver current while I_charge > 0, open REGEN within one tick and count it
  (a named diagnostic, not a latch at first).
- **Rejected or deferred:** the "always-powered charger" (Option A of the review) keeps REGEN
  closed at bus level and relies on layer 2 alone - REJECTED under R3. Opening `MOT_PWR` during
  braking (isolating V-MOT from the bus) also removes the path, but re-closing it onto a V-MOT the
  charger has drained is the Death-5 hot-plug that destroyed boosts - DEFERRED, hardware review
  needed.
- **Consequence for the operator's speed concern:** with layer 1 the charger must boot AND react
  inside the burst. If M1 shows that cannot happen, regen harvest on this board needs a hardware
  change (for example a hardware comparator gating REGEN EN on V-MOT > V_bus, or a different
  charger/path), and fw v37 keeps the interlock and the diagnostics only.
- **Common items:** the UV backoff takes precedence over regen; charger I2C/INIT faults do not latch
  until the charger has ACKed once this boot; `LIMIT_V_RGN_MAX` re-derived to <= ~26 V true.

## 4. Telemetry protocol v5 (R4: approved)

Implement with the `protocol-bump` skill (byte count, checksum span, PLAN.md section 6b, tests,
and the Pi bridge in lockstep). The v4 fields keep their offsets; the new fields are appended
before the checksum, so a bridge can tell v4 from v5 by length.

Proposed additions (sizes to be finalised in the round):

| Field | Type | Why |
|---|---|---|
| `proto_version` | u8 | the packet identifies its own layout from now on |
| `fw_version` | u16 | WORK_QUEUE 0j item 1: every bag records the firmware that produced it |
| `blg_file_index` | u16 | the SD log currently recording (0 = none); pairs bags with BLGs (section 5) |
| `blg_prefix` | u8 (ASCII) | `M`/`Y`/`W`/`D`/`P`/`T` for ML/YP/WP/DC/PS/TP |
| `I_cmd` | f32 | the commanded motor current: the regen trigger and the drive loop's output, today invisible to the Pi |
| `charger_flags` | u8 | `ag105DataValid`, `ag105Configured`, settled, `MPPT_DISABLE` level, `ag105MeasUnavailable`, `chargerHasPower()`, regen armed, `FC_CHARGE_ALLOWED` |

Size: 58 + 11 = 69 B before any padding. Bridge side: unpack v5, keep `/vehicle_state` at 18
elements for the existing scripts, and publish the new fields plus the already-parsed Teensy
`millis()` timestamp and packet counter on a new latched-plus-periodic topic (e.g.
`/teensy_meta`). The bridge today parses the timestamp and counter but republishes neither.

## 5. Pairing rosbags with SD (BLG) logs

**Today there is no reliable way.** The bag does not carry the Teensy's clock, packet counter or
log number, and the BLG has no wall-clock time (no RTC timestamps are set on the files; the BLG
header carries `fw_version` and parameters but no date). Matching would rely on upload notes and
on cross-correlating signals both logs carry (V_bus, I_fc, I_batt, v_act).

**Adopted: layers 1 and 3 (operator, 2026-11-04).**

1. **Exact link (telemetry v5 + bridge):** the packet carries `blg_prefix` + `blg_file_index`
   while a log is recording, and the Teensy `millis()`. The bag then names its BLG(s), and the
   two clocks are the same oscillator: BLG `t_us` is `micros()`, so
   `t_us ~= (millis * 1000) mod 2^32`, giving sub-millisecond alignment without
   cross-correlation. A small tool (`tools/pair_logs.py`) reads a bag, lists the BLGs it saw, and
   writes the time offset.
2. **(DROPPED, operator 2026-11-04) RTC timestamps on the SD files.** The Teensy 4.1 RTC is set
   from the PC clock only when Teensy Loader programs the board, and it keeps time across power
   cycles only with a coin cell on the Teensy's VBAT pad. The board BOM lists no coin cell, and the
   Teensy is powered from the bench, so after any power cycle the RTC restarts from an arbitrary
   date and drifts. It cannot be trusted as calendar time; layer 1 makes it unnecessary.
3. **Repo convention for uploads:** one folder per bench session, for example
   `logs/sessions/2026-11-05_regentest/` holding the bag folder(s), the BLG(s) with their analysis
   folders, and a short `SESSION.md` (date, operator, fw version and flags, Pi node versions, EMS,
   drive cycle, which BLG belongs to which bag, notes). The pairing tool writes or checks the
   pairing table in `SESSION.md`. The existing flat `logs/ML####` and `logs/rosbags/` stay as they
   are.
