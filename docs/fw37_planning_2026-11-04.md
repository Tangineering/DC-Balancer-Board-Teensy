## 2. Answers to the operator's questions

**Is the Ag105 powered by default on the current firmware?** No. The board gives the charger
input power through only two switches: `FC_CHARGE_ENABLE` (bus -> charger, through D-BC-FC) or
`REGEN_ENABLE` (motor node V-MOT -> charger, through D-BC-RG). The firmware's own test is
`chargerHasPower() = FC_CHARGE || (REGEN && MOT_PWR)` (:14670). On v35/v36:

- `FC_CHARGE` never opens in Run (`FC_CHARGE_ALLOWED 0`, :2492); it opens only for the 10 ms
  State-99 cap drain and the State-98 `'5'` key.
- `REGEN` opens only while the commanded motor current is below -0.1 A (:13747).

So in Init, Idle and almost all of Run the Ag105 has **no input power**, cannot answer I2C, and
telemetry reports `charger_status` 0 and `I_charge` 0. It is powered only for the brief REGEN
flickers (20-200 ms in the bags). The firmware waits 500 ms of continuous power
(`AG105_SETTLE_MS`, :2360) before it trusts or configures the charger, and every power loss
resets that, so on this board the charger has never been configured from firmware in any
recorded run. Its EPROM may still hold the factory default (4.2 V / 1 A), which would not charge
a 2S pack at all. That is why the B1 bench test (section 3.1) comes first.

**What "the bus feeding the charger" means (R3).** The motor node V-MOT is connected to the
16 V bus through the `MOT_PWR` ideal-diode switch, which is kept closed through Idle and Run
(the Death-5 pre-charge rule). So whenever the firmware closes `REGEN`, the charger's input sees
the bus voltage (~15.8 V), regen or not. The bags show exactly this: during every REGEN tick
V_chg read V_bus - 0.09 V while the regen node was flat. If the charger were configured and
enabled at that moment, it would draw its charge power (up to ~24 W, ~1.5 A of bus current at
2.5 A charge) **from the bus, i.e. from the fuel cell and battery boosts**, not from braking:

- the battery share is a loop (battery -> BT boost -> bus -> charger -> battery) that only loses
  energy (two conversions at ~88 % each);
- the fuel-cell share is FC -> pack charging, which `FC_CHARGE_ALLOWED 0` was meant to forbid;
- it is a large new bus load that the UV backoff does not currently cover (regen outranks it,
  :13784 before :13806).

The ruling R3 asks: is any of that ever wanted (for example as a deliberate way to test the
charger), or must the firmware guarantee the charger only takes energy when V-MOT is ABOVE the
bus (genuine regen)? The threshold method in section 3.2 gives that guarantee in the charger
itself, provided the threshold sits above the bus; a held REGEN arm without it does not.

## 3. Regen: findings, measurements, and the fw v37 design

### 3.1 Bench gate B1 (zero code, State 98) - run before any regen firmware change

`G` (bus and motor node up) -> `4` (REGEN HIGH: the charger now has ~15.8 V from the bus) ->
wait >= 5 s -> `I` (does 0x30 ACK?) -> `S` (status byte, CHARGER_STAT, `ag105Configured`,
I_charge) -> `N` (reg 0x02 threshold, input voltage) -> `M` (release MPPT) -> `S` -> `4` off.
Clamp-meter the charger's VBAT+ lead; watch I_batt and V_bus. Also: DMM on VCHG with BT_SEQ
high and the charger unpowered (D-BT-SQ orientation: ~0 V = schematic, ~pack voltage =
reversed); DMM on V-MOT vs the pin-39 reading (the V_rgn 0.85 scale).

| B1 outcome | Meaning |
|---|---|
| No ACK at 0x30 | charger power or I2C problem; firmware cannot help |
| ACK, status 0x00, STAT 1 pulse, no current | consistent with the VBat- wiring defect (R2) |
| ACK, charges from the bus | the charger works; the remaining blockers are firmware timing and test design |

### 3.2 The operator's concern: is the Ag105 fast enough for a regen burst?

What the bags show about the burst (RegenTest_v2, six decels from 2 m/s, fw <= v35,
`docs/reviews/fw36_regen_2026-11-04/figs/regentest_decels.png`): V-MOT rises 0.08-0.12 s after
the setpoint falls, peaks at the chopper clamp (~21.4 V true) 0.10-0.20 s in, and is back at bus
level by 0.3-0.6 s. Braking work above friction is ~0.8-1.0 J per decel, ~0.7 J electrical:
roughly 0.2 A into the pack for 0.4 s, if captured.

What the datasheet says (AG105_Silvertel.pdf, MPPT section): the threshold (11-33 V, reg 0x02 or
MPPTS) "must be present across the input ... before charging will commence"; MPPT "can be enabled
or disabled without restarting the module or terminating charge". **It gives no response time,
no start-up time and no Bring-Up duration.** So the concern is real and unanswerable from the
documents: `TODO(verify: Silvertel)` and measure.

The threshold method removes the firmware's 500 ms settle and the module's boot time (the charger
stays powered and configured), but not the module's own reaction time to its input crossing the
threshold, nor any Bring-Up phase it runs at the start of each charge.

**Measurement M1 (decides R1):** after B1 passes, in State 98 with REGEN held and the charger
configured: set reg 0x02 just above V_bus (`N`), release MPPT, then step the threshold below
V_bus and back above (two `N` writes). Scope the charger input current (or VBAT+ current) and
time onset and release. Then repeat on a real RegenTest decel with a 1 kHz `'K'` BLG running.

| M1 result | Consequence |
|---|---|
| Onset << 100 ms | threshold method is viable as designed |
| Onset ~ 100-300 ms | captures only the tail of each burst; consider lengthening the burst: a lower VESC "Battery Current Regen Max" (longer, gentler braking), or more V-MOT capacitance (hardware) |
| Onset > ~0.5 s or a Bring-Up per event | the Ag105 cannot harvest these bursts on this board; regen harvest needs a hardware path or a different charger; keep the firmware diagnostics only |

### 3.3 fw v37 regen design (R3 = no bus-fed charging; R1 pending M1)

**The Ag105 has no charge enable.** Table 7 lists no enable/disable register (0x00 current,
0x01 voltage, 0x02 MPPT threshold, 0x03 timeout, 0x04 recovery, 0x05-0x07 measurements, 0x0A
JEITA, 0xE5/0xE6/0xFD/0xFE housekeeping), and the module's only control pins are MPPTD and LD
(load output disable). So "the charger decides not to charge" can only mean its input threshold
(reg 0x02, EPROM, written over I2C), and that threshold may not even apply while MPPTD is LOW,
which is exactly how v35/v36 hold it during regen. A threshold is a setting, not an interlock:
it was never acceptable as the only thing standing between the bus and the charger.

**Why the hazard exists at all.** V-MOT is both the motor's supply and the regen node. With
`MOT_PWR` closed (kept closed through Idle and Run since Death 5), closing `REGEN` connects the bus
to the charger input. Scale of the loop: bounded by the charger's own current limit (2.5 A charge,
~24 W input, ~1.5 A of bus current), so it is not a runaway, but it wastes ~25 % of what it
circulates, draws FC power into the pack (what `FC_CHARGE_ALLOWED 0` forbids), loads the FC toward
its 1.4 A OC trip, and sits outside the UV backoff today.

**Design rule for fw v37 (R3):** the regen switch may be closed only while the bus CANNOT supply
the charger, i.e. while braking holds V-MOT above the bus. The RT1987s have back-to-back MOSFETs
(RT1987 DS, "true reverse current blocking"), so a switch held off blocks both directions and a
firmware interlock on `REGEN_ENABLE` is a real physical break.

- **Layer 1 (primary, firmware interlock at 1 kHz):** close `REGEN` only when calibrated
  V_rgn > V_bus + margin (MOT_PWR's ideal diode is then reverse-biased, so no bus current can flow
  to V-MOT), and open it as soon as V_rgn falls back toward V_bus. Requires the V_rgn calibration
  (the 0.85 scale) first, and the decision must run in the 1 kHz loop, not the 50 Hz
  `chargingControl()`. Cost: the charger is unpowered until the burst starts, so its boot time
  eats into a 0.3-0.6 s burst (M1 measures how much).
- **Layer 2 (independent, in the charger):** reg 0x02 set above the bus (e.g. 17.86 V) with MPPT
  RELEASED while REGEN is closed, so a layer-1 failure still finds the charger refusing a ~16 V
  input. Never hold MPPTD LOW with REGEN closed until the datasheet question "does MPPTD-low bypass
  the threshold?" is answered. Note the factory default (0xFF with MPPTS open = 18 V) is also above
  the bus; a v24-era EPROM write could have left 12.3-13.4 V, so read reg 0x02 back before relying
  on it.
- **Layer 3 (backstop detector):** while REGEN is closed, if V_rgn is within the margin of V_bus,
  or the bus sources deliver current while I_charge > 0, open REGEN within one tick and count it
  (a named diagnostic, not a latch at first).
- **Rejected or deferred:** the "always-powered charger" (Option A of the review) keeps REGEN
  closed at bus level and relies on layer 2 alone - REJECTED under R3. Opening `MOT_PWR` during
  braking (isolating V-MOT from the bus) also removes the path, but re-closing it onto a V-MOT the
  charger has drained is the Death-5 hot-plug that destroyed boosts - DEFERRED, hardware review
  needed.
- **Consequence for the operator's speed concern:** with layer 1 the charger must boot AND react
  inside the burst. If M1 shows that cannot happen, regen harvest on this board needs a hardware
  change (for example a hardware comparator gating REGEN EN on V-MOT > V_bus, or a different
  charger/path), and fw v37 keeps the interlock and the diagnostics only.
- **Common items:** the UV backoff takes precedence over regen; charger I2C/INIT faults do not latch
  until the charger has ACKed once this boot; `LIMIT_V_RGN_MAX` re-derived to <= ~26 V true.

## 5. Pairing rosbags with SD (BLG) logs

**Today there is no reliable way.** The bag does not carry the Teensy's clock, packet counter or
log number, and the BLG has no wall-clock time (no RTC timestamps are set on the files; the BLG
header carries `fw_version` and parameters but no date). Matching would rely on upload notes and
on cross-correlating signals both logs carry (V_bus, I_fc, I_batt, v_act).

**Adopted: layers 1 and 3 (operator, 2026-11-04).**

1. **Exact link (telemetry v5 + bridge):** the packet carries `blg_prefix` + `blg_file_index`
   while a log is recording, and the Teensy `millis()`. The bag then names its BLG(s), and the
   two clocks are the same oscillator: BLG `t_us` is `micros()`, so
   `t_us ~= (millis * 1000) mod 2^32`, giving sub-millisecond alignment without
   cross-correlation. A small tool (`tools/pair_logs.py`) reads a bag, lists the BLGs it saw, and
   writes the time offset.
2. **(DROPPED, operator 2026-11-04) RTC timestamps on the SD files.** The Teensy 4.1 RTC is set
   from the PC clock only when Teensy Loader programs the board, and it keeps time across power
   cycles only with a coin cell on the Teensy's VBAT pad. The board BOM lists no coin cell, and the
   Teensy is powered from the bench, so after any power cycle the RTC restarts from an arbitrary
   date and drifts. It cannot be trusted as calendar time; layer 1 makes it unnecessary.
3. **Repo convention for uploads:** one folder per bench session, for example
   `logs/sessions/2026-11-05_regentest/` holding the bag folder(s), the BLG(s) with their analysis
   folders, and a short `SESSION.md` (date, operator, fw version and flags, Pi node versions, EMS,
   drive cycle, which BLG belongs to which bag, notes). The pairing tool writes or checks the
   pairing table in `SESSION.md`. The existing flat `logs/ML####` and `logs/rosbags/` stay as they
   are.

## 6. Current noise, the flywheel rotation component, and the encoder bad tooth

Two agents (2026-11-04): a current-spectrum analysis of all 21 moving bags, and a history of the
encoder decoder with a fresh census of the August SD logs. Figures:
`docs/reviews/fw36_regen_2026-11-04/figs/noise_*.png`. Orchestrator check: ML0203 shows 128 dips
spaced exactly 178 encoder counts apart (verified from `logs/ML0203/ML0203.csv`).

### 6.1 What the current noise is (Pi bags, 2026-09-07 .. 10-30, fw <= v35)

- **Rotation-locked, very high confidence.** In 635/635 steady-speed windows the dominant
  current peak sits on a flywheel-rotation order (86 % at exactly 1x, the rest at 2x, the tire's
  2.31x, or 3x). f_rot = v / (2 pi x 0.0762 m) = 2.089 Hz per m/s (`FLYWHEEL_RADIUS_M` :2644,
  `ENCODER_SLOTS_PER_REV` 90 :2620). The ratio holds from 1.0 to 4.2 m/s, so it is not an alias.
  The 3.9-4.7 Hz peak behind the OC_FC latches is the 1x line at SDP cruise speed.
- **Mechanism: the drive loop chasing a ripple in `v_actual`.** Coherence between `v_actual` and
  I_tot at f_rot is 0.97-1.00; the shipped `drive_controller_coeffs.h` reproduces both the gain
  (|C| = 86 / 79 / 75 / 73 A per m/s at 2.1 / 3.1 / 4.6 / 5.6 Hz) and the 133-146 deg phase. The
  loop's crossover is 2.76 Hz, on top of the 1-5 Hz rotation band, and |S| >= 1 above ~2 Hz, so
  the loop amplifies a 1x disturbance there instead of rejecting it. Result: +/-1.1-1.5 A of motor
  current and 0.10-0.19 A rms of bus current, split between FC and BT by the share (FC fraction
  tracks the DC share, median ratio 0.98). Present with the FC off (10-26, share 0).
- **Noise budget, I_tot (HP > 0.7 Hz, purges excluded, mA rms):** 1.0 m/s: 80-96 total, of which
  49-71 rotation-locked, 37-40 broadband, 3.3 quantization; 1.5 m/s: 114-121 / 99-108 / 42-44;
  2.2 m/s: 172-189 / 155-168 / 64-77; 2.7 m/s: 190-195 / 151-159 / 94-100. Two fixed lines at
  4.10 and 6.93 Hz (~10 mA each, origin unknown). 09-07 is a different phenomenon (a ~10 Hz
  anti-phase FC/BT exchange at share command 0.06).
- **OC_FC link:** on the two SDP latches the I_fc 1x amplitude was 0.18-0.22 A on a 0.83-0.88 A
  mean, crests every 0.2 s = f_rot; the 1.4 A trip fell on an unsampled crest.
- **The ripple grew between 09-07 and 10-20** (v ripple 3.9 -> 13-15 mm/s at 2.2 m/s; current
  0.040 -> 0.15-0.165 A). Mechanical, encoder, or firmware; the bags cannot say.

### 6.2 The bad tooth: history, and whether the mitigation worked

- **It was real and it is well-defined in the August SD logs (fw v18/v19, 90-slot disc).** The
  encoder loses 2 counts per revolution (dips exactly 178 counts apart in ML0194/0195/0203,
  TP0205/0212, WP0213, YP0214). Once per rev `v_act` reads 0.50x for ~1 slot with 0.65x shoulders
  (the N = 2 average over stored periods [T,2T] -> [2T,2T] -> [2T,T]); `I_cmd` answers with a +7 to
  +9 A pulse within ~3 ms, decaying over ~40 ms; mean `v_act` biased -0.8..-1.3 % (the recorded
  -0.9 % steady-state error). The excursion is an estimator artefact (a real 0.5 m/s drop in 3 ms
  would need ~580 N), but the +8 A pulse is real torque, so the artefact also injects a real
  once-per-rev speed ripple. Recorded only in `test/CLAUDE.md:13-16` (2026-08-25b; "physical
  inspection is the fix", standing order at `test/CLAUDE.md:67`); no ledger row; no record that
  the disc was ever inspected. The "counts 42-74 mod 180" location quoted then is a DRIFTING
  coordinate (2 counts per rev), not a disc angle.
- **The firmware mitigations never targeted it.** fw v12 (edge-period estimator), v13 (adaptive
  low-side gate, stale bound), v15 (pitch count from `|dpos|`), v17 (fractional-pitch ledger,
  hold-until-corroborated), v18 (90-slot disc), v28 (direction auto-flip) closed the x2 and 1/2
  absorbing basins and the spurious-edge chatter (spurious drops now 0.06-0.14 per rev). The
  lost-count case is accepted on purpose at `.ino:15399-15404` ("reads low -> the loop drives, it
  does not brake"). The host harness (`docs/encoder_defect_harness.md`) models a deleted slot,
  not a per-rev periodic one, nor A/B hitting at the real 10.75-pitch sensor separation, nor a
  pitch/edge-position error. **Verdict: the basin and chatter fixes work; the bad tooth was never
  mitigated.**
- **But the Pi-era bags do not show the bad tooth.** Zero sub-0.8x dips in ~90 k steady samples
  (a 3.3 % duty dip would have appeared thousands of times); the folded-on-angle waveform is a
  smooth 1x (+ some 2x) sine, 30-51 mm/s p-p, reproducible between run halves at 0.81-0.98, and a
  matched-filter search bounds any single-slot error below ~0.5 % of a pitch (which could put at
  most ~0.01 mm/s into 1x). So between 2026-08-25 and 09-07 either the disc or sensors changed
  (nothing records it - **operator question Q1**) or a second, smooth once-per-rev source took
  over. The tire-rate (2.31x) line also appears in `v_actual`, which a disc on the flywheel
  cannot fabricate, so at least part of the ripple is genuine mechanical speed modulation.
  Candidates: disc eccentricity (artefact), flywheel runout/imbalance (real), roller/tire
  contact runout (real); the "external" component is ~13-14 mm/s flat from 1.0 to 2.7 m/s, which
  fits neither a pure eccentricity (grows with v) nor a constant force (shrinks as 1/v).
- The student's fw v31-v36 do not touch the encoder path, the drive controller or the BLG record.
- Conflicting records on whether the 74HC14 Schmitt buffer is fitted: `test/CLAUDE.md:7` says it
  is; ledger row 18, the archive and the `.ino` comments say it is outstanding (**Q2**).

### 6.3 Are SD logs required? Yes.

The bags are 50 Hz with no `I_cmd`, `encoder_pos`, `u_unsat` or estimator fields; they cannot
separate an encoder artefact from real speed ripple, and their 25 Hz Nyquist is below the slot
rate (188 Hz per m/s) and the motor orders (15.8x, 31.7x). BLG v9 already carries `t_us`,
`v_act`, `I_cmd`, `u_unsat`, `encoder_pos`, `enc_period_ref_us`, the multi-pitch/spurious-drop
counters, per-channel edge counts and the phase/duty EWMAs at ~885 Hz, which is enough for the
census, the counts-per-rev, the loop-vs-mechanical question and the C(f_rot) check. For an exact
per-slot pitch map, BLG v10 should add ~13 B: the last accepted A-rise `micros()`, `encPosAtLastEdge`,
the last stored period and `posMag` (every A-rise then lands in some record below 5.3 m/s).

**Bench capture (fw v35 as flashed, card fitted, car on the dyno):**
1. `T` -> State 98; `G` staged bring-up; `S` dump (phase ~0.25, duties ~0.50).
2. **Count check:** `L` on, hand-turn exactly 10 revolutions, read the change in `enc_pos`: 1800 =
   healthy, 1780 = one slot lost per rev; `L` off. (The gate for everything else.)
3. `K 1` (manual log).
4. **Open-loop current holds:** `A` 3.0 / 3.4 / 3.8 / 4.2 A, >= 30 s each after settling (drag law
   predicts ~0.5 / 1.0 / 1.5 / 2.0 m/s). `I_cmd` is flat by construction, so any 1x in `v_act` is
   encoder or mechanics, not the loop. (`T 3.8 30 0.5` is an auto-logged alternative.)
5. **Coast-downs** from the 4.2 A hold (`A 0`), x3: 1x content with no motor torque.
6. **Closed loop:** `X`, then `V` at 0.5 / 1.0 / 1.5 / 2.0 m/s, 30 s each.
7. `K 0`. If possible, VESC Tool RT data (ERPM, motor current) during step 4 as an
   encoder-independent speed reference. Scope A and B at 1 MS/s for >= 2 revolutions during a hold.
8. Mechanical: dial-indicator runout of the flywheel rim and of the disc; re-seat the disc 90 deg
   on its hub (the 1x phase relative to flywheel runout moves only if the disc is the source).

**Analysis:** (a) dip census and counts per rev; (b) revolution-synchronous averaging of `v_act`,
`I_cmd`, `I_fc + I_batt`, orders 1-10 plus the motor orders; (c) open-loop holds: a fractional
`v_act` pattern identical at every speed and current is geometric (encoder); amplitude scaling as
1/omega or with load is real; (d) closed loop: measured `I_cmd`(1x) / `v_act`(1x) vs C(f_rot);
(e) coast vs hold vs ERPM; (f) bus-side 1x with flat `I_cmd` points at the VESC/motor; re-run
`tools/rail_spectral` (merged 2026-11-04, **Q5**) for order 1.

### 6.4 Options for decoder robustness (ranked; 3-6 touch `doEncoderA` / `updateWheelSpeed`,
which CLAUDE.md protects, so each needs an explicit operator exception as v13/v15/v17 had)

1. **Find out whether the tooth still exists** (step 2 above; near-zero cost). Gate for the rest.
2. **Repair or replace the disc** if it does. Root fix. The Schmitt buffer does not fix a missing
   or blocked slot or an eccentric disc; it only addresses chatter.
3. **High-side outlier hold in firmware:** mirror the low-side gate - while armed, an accepted
   interval longer than ~1.6x ref, or `posMag` < 2 on a full-length interval, holds the last
   reading for one pitch. One compare. Median-of-3 would NOT work on the measured signature (two
   consecutive 2T periods: median of [T,2T,2T] is 2T); median-of-5 costs ~2 pitches of delay. Arm
   at >= ~0.5 m/s (genuine deceleration bounds the per-pitch ratio at 1.19 there, 1.52 at
   0.36 m/s). Tests: new harness families (per-rev periodic missing slot; A-only / B-only at the
   real sensor separation; pitch / edge-position error) and a byte-identical pin on nominal streams.
4. **Learned per-slot pitch table** (p_k for k = slot index mod 89/90): fixes a bad tooth and
   eccentricity alike with no added delay, but there is no index sensor, counting breaks on every
   lost count or spurious drop, and a wrong index injects the same-size error elsewhere; needs a
   lock/confidence state with fallback, offline learning from constant-current holds first.
   Highest complexity.
5. **Full-revolution estimator** (time per 90 A-rises): immune to per-slot geometry but half a
   revolution of group delay (120-480 deg at 2.76 Hz): unusable in the loop; useful as a `v_rev`
   diagnostic and as the teacher for option 4.
6. **Index sensor** (hardware): makes option 4 robust.
7. **Lower the drive bandwidth** (re-synthesis, not a filter): last resort; a notch at f_rot is
   not available without destroying the loop.

Independent of the decoder: the OC_FC persistence fix (section 7 item 1) removes the trip that

### 9.1 Change 1: the drive control law, re-synthesised at a lower crossover

Why it should work: the current ripple is the drive loop acting on a once-per-rev `v_actual`
ripple (section 6.1: coherence 0.97-1.00, gain and phase reproduced by the shipped coefficients).
With the setpoint constant, the 1x motor-current tone is |C(f_rot)| x the `v_actual` tone, and the
loop sits at |S| >= 1 across the rotation band (crossover 15.98 rad/s = 2.54 Hz design, 2.76 Hz
measured; |S| peak 1.4-1.5 at 4.7-5.1 Hz). Lowering the crossover lowers |C| across 2-6 Hz roughly in
proportion and pulls the |S| peak below the band, so the loop stops amplifying the ripple. The
share loop and the droop path are untouched; they only see a smaller bus-current ripple.

The synthesis is `controller_design_MIMO/synthesize_drive_siso.py` (H-inf mixed sensitivity:
`WC_TARGET` sets the Wp corner, `WU_DC, WU_WC, WU_HF` the control-effort weight; the shipped rung is
WC = 60, Wu(0.25, 300, 12.5) -> wc 15.98 rad/s, PM 51.9 deg, ||S|| 2.418). The ladder already
contains a lower rung: WC = 24, Wu(0.3, 300, 20) -> wc 8.78 rad/s (1.40 Hz), PM 57.8 deg,
||S|| 1.589, which the round rejected only on its bandwidth gate. Expected effect of that rung at
the rotation band: |C| down ~0.55x and the S-peak amplification (1.4-1.5x) gone, i.e. roughly
2.5-3x less current ripple; a rung near wc 5-6 rad/s (~0.9 Hz) would give ~3-4x. What it costs:
slower setpoint tracking (the drive cycles ramp at <= 0.3-1 m/s^2, which a ~1 Hz loop follows with
modest lag; the RegenTest decels at 1-3.3 m/s^2 will lag more) and a slower recovery from a cut
or saturation; the ML0136 limit cycle was a delay-at-crossover effect, so a LOWER crossover is
safer on that axis, not less safe.

Round plan: (a) run a ladder WC in {12, 18, 24} x Wu HF in {12.5, 20} with the existing gates (PM
>= 45 deg, ||S|| bounded, delay margin) plus a NEW reported metric, |C(j 2 pi f)| at f = 2.1 / 3.1
/ 4.6 / 5.6 Hz against the shipped 86 / 79 / 75 / 73 A per m/s, target >= 2.5x lower; (b) pick the
rung, regenerate `drive_controller_coeffs.h`, `drive_siso_coeffs.h`, `drive_siso_metrics.txt` and
the replay vectors (`drive_replay_vectors.h`) with `validate_drive_siso.py`; (c) the firmware
changes are the generated header, `FW_VERSION 37`, the `.ino` changelog (v31-v37) and ledger row 37;
`drive_controller.h` (the DF2T / Hanus structure) is unchanged. Operator first try: lower crossover
only, Wu unchanged - the ladder reports both axes so the choice is informed.

**Measurement (the A/B):** the SD capture of section 6.3 on v35 BEFORE the flash, then the same
capture on v37; compare the 1x `I_cmd` and `I_fc + I_batt` tones at matched speeds (open-loop holds
are the control: they must be identical, since `I_cmd` is flat there), the OC_FC crest margin, and
tracking lag on a UDDS ramp and a RegenTest decel. Both with a Pi bag running under the section 5
convention.

### 9.2 Change 2: State-98 Ag105 commissioning procedure (one new key)

Purpose: talk to the charger, read its EPROM state, write its settings, and watch it, with the
Run path untouched. It feeds the charger FROM THE BUS on purpose (the only way to power it without
regen); that is the bench-attended, time-capped exception to R3, exactly as the existing `'4'`/`'5'`
keys are. Caveat before the first run: the charger-input hot-plug (D-RG-EN) has never been scoped
(`docs/boost-bringup-debug.md` watch item) - scope V_chg on the first engagement.

Behaviour (spec for the round; the key letter is chosen from the free set in the round):
- **Preconditions:** State 98; `MOT_PWR_ENABLE` HIGH (run `G` first) else refuse with a message;
  V_bus >= `V_BUS_CHARGED_THRESH`. Prints a one-line hazard notice and waits for a confirm char.
- **Power:** `assertFcChargeEnable(false)`, then `REGEN_ENABLE` HIGH through the same path as `'4'`
  (the only legal way to power the charger here), `MPPT_DISABLE` LOW (inhibited) to start. Prints the
  power edge time.
- **Auto-config inhibit:** a flag that stops `pollAg105()`'s lazy write of reg 0x01/0x00 for the
  duration of the procedure, so the FACTORY / EPROM state is read before anything is written.
  (Today the lazy config would fire 500 ms after power and overwrite the evidence.)
- **Monitor at 10 Hz** (one line each): elapsed ms since power, V_chg, V_rgn (raw), V_bus, I_batt,
  I_fc, I2C ACK at 0x30 (y/n, NAK count), `ag105_status_raw` and its Table-6 decode (GENSTAT 0-7,
  CC/CV/MPPT bits), regs 0x00 / 0x01 / 0x02 / 0x05 (V_batt x0.064) / 0x06 (I x0.011) / 0x07
  (V_in x0.141) / 0xFD-0xFE (firmware), CHARGER_STAT pin level and the decoded STAT pulse mode,
  MPPT pin level.
- **Sub-commands while running:** `r` re-read all registers; `w` write reg 0x01 = 0x08 (2S) and
  reg 0x00 = 0x01 (2.5 A) after a second confirm, then read back; `t <count>` write reg 0x02 (MPPT
  threshold) and read back (EPROM: counted against the write budget); `m` toggle `MPPT_DISABLE`
  (the M1 response-time test: with the threshold above V_bus, toggling tells whether the module
  charges or refuses); `d` reset-to-defaults (reg 0xE6) after a confirm; `q` stop.
- **Stop:** on `q`, on a 120 s cap, on any fault, or on leaving State 98: `MPPT_DISABLE` LOW,
  `REGEN_ENABLE` LOW, auto-config inhibit cleared, a summary line (ACKed? max I_charge, status
  history, settled yes/no, configured yes/no).
- **Faults:** `detectFaults()` keeps running; a GENSTAT 5/6/7 can latch `FAULT_CHARGER_STAT` - that
  is itself a result, not a hazard. The I2C/INIT latches arm only in State 2/3 and stay that way.
- **Tests:** the mock Wire's scripted byte queue covers ACK/NAK, the status/register sequence,
  the inhibit (no 0x01/0x00 write until `w`), the time cap, and the stop sequence (REGEN LOW
  before anything else is left behind).
