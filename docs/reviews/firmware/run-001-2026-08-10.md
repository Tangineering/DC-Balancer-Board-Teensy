## Round 1 — Codex adversarial review

No-ship — the SD logger can block State 99 teardown, and its decoder can publish corrupted recovery data.

Scope note: `git status` showed only review-ledger edits uncommitted; the requested SD/Y implementation is already committed in `42602d3` and `da7d787`. I reviewed that intended range.

### F1 — critical — “Non-blocking” SD I/O can stall fault teardown and live motor control

- Where: `teensy_controller/teensy_controller.ino:1315-1336`, `:1534-1592`, `:2344-2402`, `:3228-3245`; `test/mock_sd.h:86-112`
- What can go wrong: `isBusy()` is sampled before synchronous `write()`, `truncate()`, and `close()`, so it cannot bound the operation it is about to start. On a fault with an already-empty ring—a normal steady-state case—State 99 phase 0 runs, then `logFinishFile()` immediately executes. Its own comment admits `truncate()` can take “tens of ms,” while State 99 requires two 10 ms sequencing dwells before it isolates the motor/regen path. Thus the logger can hold phase 0, with `MOT_PWR_ENABLE` still high, for longer than the entire intended teardown sequence. The same issue exists during an `R` profile start: it intentionally retains the pre-existing manual motor command, then directory-scans, preallocates 32 MB, and writes a header. The host mock makes all these calls instantaneous, so the tests cannot exercise this failure.
- Recommendation: remove all filesystem operations from a live control/fault path. Preflight/open/preallocate only while the stage is physically safe, do not truncate/close during State 99, and either use a truly bounded asynchronous SDIO implementation or disable active-run logging. Scope a GPIO around every real-card operation and reject the design unless worst-case loop gaps remain below the safety budget.

### F2 — major — Decoder falsely truncates clean wrap-crossing logs and can accept stale sectors after brownout

- Where: `tools/decode_benchlog.py:81-101`; `teensy_controller/teensy_controller.ino:1427`; `test/mock_sd.h:102-104`
- What can go wrong: the decoder rejects any non-increasing `uint32_t micros()` value before it checks for a trailer. `micros()` wraps every 4,294.967296 s (71.58 min). The Y profile lasts 40 s, so any clean Y run started in the final 40 s before wrap is decoded as a truncated/brownout file, dropping all post-wrap data and hiding its valid trailer. Separately, a brownout after `preAllocate(32 MB)` leaves stale sectors; an old record sequence with timestamps greater than the last new sample passes the only validity check and is emitted as real data. There is no session ID, sequence number, or per-record integrity check. The mock deliberately does not materialize preallocation, and the Makefile never runs decoder tests.
- Recommendation: version the bench-log format and add a per-record session nonce plus monotonically increasing sequence number (and preferably CRC). Decode the sequence wrap-safely; reject any record whose nonce/sequence does not match. Add crafted host tests for a clean `micros()` wrap and monotonic stale preallocated records.

### F3 — major — Directory-read failure can erase an existing log

- Where: `teensy_controller/teensy_controller.ino:1278-1308`, `:1420`; `test/mock_sd.h:167-184`
- What can go wrong: if opening the root directory fails, `logNextFileName()` treats it as an empty directory and returns `PS0001.BLG`. The following `O_TRUNC` open can then erase an existing `PS0001.BLG`. This is reachable with the supplied one-shot mock failure: it can fail the root open, then allow the subsequent named open. No test covers that sequence.
- Recommendation: make a failed root open a hard logging refusal, never a zero-index scan. Use exclusive creation for new logs where supported, and add a test with an existing `PS0001.BLG` plus a root-open failure asserting its bytes remain unchanged.

### F4 — minor — Mid-run write errors generate an undocumented close reason

- Where: `teensy_controller/teensy_controller.ino:1578-1583`, `:1315-1333`; `tools/decode_benchlog.py:45`, `:137-141`; `test/test_main.cpp:4923-4957`
- What can go wrong: a failed record write calls `logFinishFile(false)` without setting `logCloseReason`; the trailer therefore contains reason `0`, while the documented decoder contract only defines reasons 1–5. If the trailer write succeeds, the decoder reports `unknown(0)` rather than an I/O-aborted capture. The write-error test checks continuation of the profile but not trailer provenance.
- Recommendation: add and document `LOG_CLOSE_IO_ERROR`, set it before `logFinishFile(false)`, and assert it in the write-error test.

### F5 — minor — “1 kHz” and `dropped_count` overstate capture completeness

- Where: `teensy_controller/teensy_controller.ino:651-656`, `:1478-1487`; `PLAN.md:884-887`; `test/test_main.cpp:5018-5022`
- What can go wrong: a 50 ms loop gap produces one sample, silently losing 49 scheduled samples; `logDroppedCount` remains zero because it only counts ring-full drops. The test explicitly codifies this behavior while documentation calls it a “true 1 kHz cadence.” Timestamps expose the gap only if downstream analysis notices it.
- Recommendation: record missed sample periods and maximum sample interval in the trailer/status, and describe the logger as best-effort 1 kHz.

Clean areas: the SD probe is correctly placed after deterministic safe GPIO writes; `triggerFault()` itself only sets a close flag; I found no telemetry/command framing change—the v4/58-byte telemetry and 22-byte command packet remain intact. The supplied executables report 1,018 production and 95 bench tests passing, but their SD mock cannot model blocking SDIO, real preallocation, or decoder recovery behavior.
